为什么我用纯手写 HTML 搭建了这个网站

2026 年 8 月 30 日 · 约 6 分钟 · 字数 1500

每次跟朋友说「我这个网站是纯手写的」，对方的第一反应都是： 「2026 年了？你为什么不直接用 XX 框架？」 这个问题很合理。所以这篇小文就是想认真回答一下它。

手写的三个理由

1. 完全可控

网站打开的第一毫秒发生了什么，我全部知道：浏览器拿到 HTML， 读一份 CSS，跑几十行 JS，结束。没有水合（hydration），没有依赖树， 没有「升级一个包整个站挂掉」的惊吓。我想改一个颜色， 打开 CSS 改一行，保存，刷新，完事。

2. 没有构建，就没有构建失败

我见过太多项目死于 node_modules：换台电脑， npm install 报错；半年没动，构建工具大版本一更新， 配置全要重写。而纯静态文件呢？

网站应该像一张纸：拿起来就能读，十年后还能打开。

这个网站的所有文件，双击就能在浏览器里打开——连服务器都不需要。 只要 HTML 还被这个世界支持（它已经支持了三十多年，并且还会继续）， 这个网站就还活着。

3. 它逼我回到基本功

写框架久了，很容易忘记一些基本问题：一个 <button> 的默认行为是什么？焦点应该落在哪里？屏幕阅读器会怎么读这个区域？ 手写的意思是——这些决定都摆在你面前，躲不掉。

整个网站的核心就这几行

<!-- 网站的全部骨架，就是这样 -->
<html lang="zh-CN">
  <link rel="stylesheet" href="css/style.css">
  <script src="js/main.js"></script>
</html>

代价是什么？

公平起见，也说说坏处：

  • 加新文章要复制一份模板文件，改标题、改正文——没有 Markdown 那么爽；
  • 没有标签系统、全文搜索这些「白送」的功能，想要就得自己写；
  • 多人协作？不存在的，这是我一个人的小屋。

但对个人网站来说，这些代价几乎可以忽略。更新的频率不高， 功能的需求不大，反而是「永远能打开」这件事价值最大。

所以，什么情况下该用框架？

当你的网站需要「数据」的时候——大量动态内容、用户系统、复杂状态—— 框架就是正确的工具，这也是我吃饭的家伙。工具没有高低， 只有合不合适。

而一个个人网站的本质，其实就是几页纸： 我是谁，我做过什么，我怎么想。 用纸和笔就够了。
